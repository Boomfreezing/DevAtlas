# 多目录文件树：渲染预算与并发读取

更新日期：2026-09-12。继[单一宽目录阶段](./FILE_TREE_BROWSER_PERFORMANCE.md)之后，本轮检查目录密集、多个小目录同时展开与快速项目切换。仅完善现有文件树，没有新增菜单、后端接口、依赖库或数据表；不调用真实模型、不同步用户仓库、不推送 GitHub。

## 修复的问题

原窗口化阈值只计算一个目录中的文件数量。24 个目录各有 100 个文件时，每个都未超过 600，但同时展开会累计挂载 2,400 个文件行。原请求隔离可以防止旧结果回填，却没有跨目录并发预算。

- 现在按整棵树中已展开目录的可展示元数据计算预算，超过 600 条时，各目录文件页均参与窗口化；远处文件保留高度占位，滚回复用已读取数据。
- 预算采用按生命周期登记的句柄，追加页更新原计数，折叠释放对应计数。只有跨越阈值时才通知文件页，避免每次请求都触发全树更新。旧句柄不能解除新生命周期登记。
- 每棵树的目录读取最多 4 个并发，等待项按先进先出执行。排队时折叠、离页或切换项目，会取消排队项，不再真正调用读取接口。已经开始的任务，需实际结束才释放槽位。
- 沿用 AbortSignal 与缓存条目身份双重校验，保留项目及分析代际隔离。开发环境 StrictMode 的清理与重挂载不会永久关闭队列。
- 固定同一项目、同一概览标签下的耦合入口回调，减少无关 App 状态更新引起的文件行重渲染。
- 保留绿色 Terminal 样式、目录组件身份、折叠缓存、分页控件与原菜单结构；阈值切换时重新核对文字选区，防止丢失当前选中内容或保留过期选区。

## 测量方法

脚本：[file-tree-dense.spec.ts](../frontend/perf/file-tree-dense.spec.ts)。原始记录：[修改前](./performance/file-tree-dense-baseline.json)、[修改后](./performance/file-tree-dense-after.json)。

1. 600 个根目录，按 200 → 400 → 600 加载，作为未窗口化目录的控制组。
2. 24 个目录分别含 100 个文件，逐一真正展开，保留全部展开状态与 2,400 条文件记录；不能通过少读数据或折叠目录制造收益。
3. A 项目子目录读取未完成时，通过项目选择器 A → B → A，再释放旧响应，验证当前项目与重新展开后的文件。

每个场景各 3 个独立浏览器页面样本。业务 API 全部由合成响应提供；使用本机 Chrome、1440×1000 视口、Vite 开发模式与 StrictMode，测试服务仅使用 8011/5175，临时数据在 D 盘。计时含 Playwright 通信、交互与两帧等待，不等于纯渲染耗时或真实后端端到端延迟。

堆数据来自 CDP 强制 GC 后的 JS heap，并非进程 RSS、自然 GC 观测或峰值内存。前后分开测量、每组仅 3 次，不作统计显著性、P95 或任意设备固定提速承诺。首次脚本调试碰到 StrictMode 双请求，修正后重新采集完整基线；此前单元测试已结束，没有与正式基线或优化后测量同时运行。

基线保留采样时的源码哈希；采样后仅将取消字段明确命名为 `tree_request_abort_observed_including_strictmode`，数值未改。这个字段包含 StrictMode 取消，不能单独作为项目切换取消次数。优化后记录另外包含本轮新增队列与预算源码的哈希。

## 实测结果

以下为 3 次样本中位数（Chrome 152.0.7977.83、Node 24.18.0、Windows）。没有合并或替换上一阶段的单目录、后端 SQL 测量。

| 场景 / 指标 | 修改前 | 修改后 |
|---|---:|---:|
| 24 目录累计已读取文件 | 2,400 | 2,400 |
| 同时保持展开的目录 | 24 | 24 |
| 挂载文件行 | 2,400 | 200 |
| 树内元素数 | 19,417 | 1,817 |
| 强制 GC 后 JS 堆 | 29.40 MiB | 10.65 MiB |
| 第 24 个目录展开 | 986.62 ms | 73.89 ms |
| 24 次展开耗时合计 | 10,021.90 ms | 2,308.94 ms |
| 600 个纯目录：挂载目录行 | 600 | 600 |
| 600 个纯目录：强制 GC 后 JS 堆 | 10.68 MiB | 10.75 MiB |
| 600 个纯目录：根目录首批读取 | 108.49 ms | 117.69 ms |
| A → B → A：两次切换合计 | 182.08 ms | 182.23 ms |

主要收益来自多目录文件行回收。两版读取量与展开目录数相同；200 行是固定视口下观测值，不是所有交互状态的上限。纯目录控制组没有减少 DOM，堆和首屏耗时有小幅增加；项目切换耗时相近，前后均未被晚到响应污染，不宣传这两项提速。

### 手动验收

1. 在已有大仓库的文件树展开多个各含几十至几百文件的目录，滚到末尾，再滚回首部：目录应保持展开，远处文件恢复无需重新读取。
2. 快速展开多个目录，再折叠尚在等待的目录：最多 4 个目录读请求同时进行；被折叠的等待项不应继续发送。
3. 读取中快速切换 A → B → A，旧目录内容或错误不应出现在当前项目。返回的文件树仍按原设计重新从根目录开始。
4. 用 Tab / Shift+Tab 穿过两个相邻展开目录的边界；改显示比例并再次滚动，文件操作和焦点应保持可用。

## 适用边界

- 600 是可展示元数据的启用阈值，包含目录项，不是实际 DOM 硬上限。只有文件行窗口化；目录节点、焦点页、选区相关页仍会保留。
- 4 是单个文件树实例的客户端目录读取并发，不是后端全局限流。切换项目会建立新作用域；旧请求取消不能保证服务端已开始的计算立即停止。请求慢时，排队也会增加后续目录的等待时间。
- 已展开目录的数据仍随用户加载量增长，不能宣称浏览器内存有全局硬上限或任意仓库都不卡顿。缺少 observer 的浏览器回退完整渲染。
- 600 个纯目录的 DOM 没有减少。本轮未增加目录虚拟化，避免未验证的高度估计和展开状态丢失；更深、更大的目录结构仍需另行验收。
- 切换菜单仍会卸载文件树，返回时重新读取根目录，不恢复此前全部展开状态。浏览器原生查找不能覆盖所有未挂载文件名。
- 本轮未改后端；250 项后端测试、85.71% 覆盖率是前一阶段结果，不计为本轮重新执行。
