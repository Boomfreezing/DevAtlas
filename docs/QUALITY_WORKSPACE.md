# 质量检测：筛选一致性、分页与长列表验收

更新日期：2026-09-12。本轮深化现有质量检测页面，不新增产品菜单、不修改六类规则或评分权重、不调用真实生成模型、不推送 GitHub。绿色 Terminal 样式沿用现有组件。

第 1～5 节保留质量分页优化时点的测量与问题记录；第 6 节记录随后落实建议的结果。旧性能数字不是后续代码重新测量的数据。

## 1. 已完成的改进

| 场景 | 现在的行为 |
| --- | --- |
| 筛选后切到其他菜单再返回 | 保留当前项目已完成的筛选与分页；继续加载使用原来的下一偏移，不回到默认筛选 |
| 快速切换范围、风险或规则 | 取消旧 GET，只有最后一次请求能更新状态；即使旧请求继续返回，也不能覆盖新结果 |
| 筛选读取或失败 | 旧问题立即退出明细，保留全局评分摘要；显示加载或错误，不把失败当作零问题 |
| 下一页请求失败 | 保留已读问题，点击“重试加载”请求相同 offset，不跳页、不丢行 |
| 返回重复页或不一致结果 | 检查 offset、limit、总量、筛选条件、重复 ID 及评分/覆盖元数据；拒绝拼接，要求重新读取当前筛选 |
| 切换项目或当前索引代际更新 | 清除旧项目/旧索引的筛选与分页，并隔离晚到的成功、错误和 loading 收尾 |
| 全量/增量分析进行中 | 暂停质量读取，等待分析结束；取消的是读取请求，不会取消用户已提交的分析 POST |
| 追加大量问题 | 按返回页保留数组引用，复用已有问题卡片和评分摘要；新增页不重复渲染全部旧卡片 |

实现拆分为 `useQualityReport.ts`（读取与缓存状态）、`qualityReportModel.ts`（纯分页校验）和 `QualityWorkspace.tsx`（现有视图）。`App.tsx` 不再同时通过项目选择、菜单切换、分析完成和分页处理器分别读取质量数据。

统计口径不变：分数、评级、三类代码评分、六类规则计数和风险总数仍是全局统计；“当前显示”是当前筛选已加载数量/匹配总数。覆盖不足和不存在代码范围的 N/A 保留，不恢复用户已删除的权重说明。

## 3. 生产构建测量

采用同一份合成的 1,500 条问题数据，100 条/页，每版 3 个独立页面样本。每个样本执行 21 次质量 GET，验证所有问题标题及顺序，包含累计 100→500→1,500 条、风险/范围筛选、零命中规则和清空筛选。没有通过减少问题、缩短描述或改变每页大小取得收益。

测量脚本：`frontend/perf/quality-report.spec.ts`。原始记录位于 `docs/performance/quality-report-production-*.json`，保存 fixture、脚本、bundle 及 bundle 内源码摘要；前后数据使用同一脚本与样本。历史文件禁止覆盖。

原始数据：[优化前](./performance/quality-report-production-baseline.json)、[优化后](./performance/quality-report-production-after.json)。环境为 Windows、Node v24.18.0、Headless Chromium 152.0.7977.83，视口 1440×1000；production 构建，不与此前图谱开发模式数据混算。两版 fixture 和测量脚本 SHA-256 分别一致。

### 测量结果

以下为每版 3 样本中位数，单位 ms：

| 操作 | 总耗时：前→后 | 浏览器脚本：前→后 |
| --- | ---: | ---: |
| 首次打开 100 条 | 101.31 → 90.60 | 5.46 → 5.88 |
| 400→500 条，追加 100 条 | 97.26 → 96.45 | 6.06 → 2.36 |
| 1400→1500 条，追加 100 条 | 176.37 → 153.67 | 14.89 → 2.60 |
| 风险等级筛选命中 | 93.68 → 88.71 | 23.40 → 17.56 |
| 代码范围筛选命中 | 46.79 → 62.79 | 3.09 → 3.21 |
| 规则筛选零命中 | 37.52 → 30.15 | 2.36 → 1.80 |
| 清空规则筛选 | 64.97 → 59.33 | 2.20 → 2.55 |
| 清空范围筛选 | 45.35 → 55.38 | 2.99 → 2.81 |
| 清空风险筛选 | 52.45 → 55.64 | 3.15 → 2.94 |

从已读 100 条逐页追加至 1,500 条的 14 步累计耗时，先按每样本求和再取中位数，为 **1,765.34 → 1,567.44 ms**。并非每一步更快：追加到 400 条为 88.72 → 96.00 ms，追加到 600 条为 101.75 → 110.70 ms；范围筛选及清空的总耗时也有回退。没有混合各样本最优值或将浏览器脚本减少直接等同于用户等待时间同比减少。

| 强制 GC 后 JS 堆 | 优化前 MiB | 优化后 MiB |
| --- | ---: | ---: |
| 打开质量页之前的应用外壳 | 2.361 | 2.481 |
| 首批 100 条 | 3.537 | 3.625 |
| 累计 500 条 | 6.564 | 5.446 |
| 累计 1,500 条 | 13.685 | 9.938 |
| 筛选后零命中 | 4.140 | 4.074 |
| 清空筛选后首批 100 条 | 4.701 | 4.599 |

大列表强制 GC 后堆下降约 27.38%，但外壳与首批 100 条略增。1,500 条时两版均保留 **22,591 个质量区域元素、15,068 个文本节点、553,496 个问题文本字符**；每个动作的元素数量和问题文本字符一致。收益来自渲染复用，不是删行或改短文案。

指标解释：

- 总耗时包含 Playwright 操作、断言、跨进程通信及两个动画帧，不是纯渲染时间或后端请求耗时。
- CDP 的 Script/Task/Layout/Style 差值作为浏览器侧诊断，不等于逐组件 CPU profile。
- 内存为计时区间外强制 GC 后的 JavaScript 堆，不是自然 GC 峰值或浏览器进程 RSS。
- 500/1,500 条对应逐次点击追加至该数量；单步耗时是最后追加 100 条的操作，不是一次返回 1,500 条。
- 仅本机三次合成样本的描述性统计，不推断 P95、统计显著性或任意真实仓库的加速比。模拟数据不用于校准评分准确度。

## 4. 尚未解决的边界

1. 本轮是**分组渲染复用，不是虚拟列表**。逐页加载后仍挂载全部问题 DOM；只保留当前项目/索引/筛选的一份缓存，但累计大列表仍会增加内存。没有宣称无限规模不崩溃。
2. 后端质量快照命中后不重新解析、评分或计算强连通分量，但每次筛选仍遍历缓存问题；冷请求还需要基础数据和评分计算。本轮模拟 API 的浏览器计时不包含这些成本。
3. 接口还没有结果版本号。前端能拒绝计数、评分、覆盖或分页结构不一致的页面，不能识别所有“元数据完全相同、内容已变”的外部更新；请求取消也不保证后端计算立刻停止。
4. 当前版本对比页在卸载时停止同步任务轮询，后端已提交的任务继续运行。若同步在离页后才完成，现有 `onSynchronized` 回调可能未执行，其他页面缓存缺少更新通知。本轮没有把这条跨模块问题误报为已修复。
5. 质量覆盖目前主要按支持解析的扩展名估算，尚未充分扣除文件过大跳过、读取失败或结构解析失败。六条静态规则也不能证明业务正确性、安全性或测试覆盖率。
6. 桌面截图确认 Terminal 风格和布局保持原样；390px 窄屏截图则发现既有筛选条不换行和卡片横向溢出。本轮未改 CSS，此问题尚未修复。浏览器行为测试通过不等于窄屏视觉验收通过。

## 5. 项目意见及下一步

目前的功能量已经足够支撑一个有完整演示链路的本科工程项目；相比继续增加菜单，更需要让现有结论可信、异常可恢复、性能有数据依据。以上判断来自当前代码与受控测试，不是对线上竞品的实测排名。

### 优先处理：后台同步与缓存更新闭环

将已提交同步任务的生命周期与页面显示解耦，让用户离开版本对比页后，当前项目的数据更新仍能被可靠感知。同步成功时使结构、搜索、质量、图谱、源码和耦合缓存按同一索引代际失效；失败保留旧源码与结果，不触发成功刷新。

验收重点是“启动同步→立刻离页→后台完成→再进入任一分析页”、同步失败、同步中切换项目、重复点击和旧请求晚到。先用受控任务测试，不需要真实 GitHub 下载或模型调用。

### 随后处理：质量分数的数据基础

区分“文件类型受支持”与“本次实际解析成功”，利用已有解析问题记录核对实际可分析范围。补充不支持语言、超限文件、语法错误、空仓库、生成代码和生产/测试混合循环的固定样本；统一页面、报告与版本对比的覆盖口径。避免因缺少解析数据而给出看似可信的高分。

这是修正已有评分输入的可信度，不以新增评分指标或重新显示权重为目标。涉及评分口径变动时更新比较来源，不能把方法变化解释为代码变好。

### 再处理：真实使用成本与交付

对真实固定版本样本补充质量冷/热请求、长列表滚动和项目往返测试，再决定是否需要窗口化或后端筛选索引。修复现有窄屏筛选换行与卡片溢出，并覆盖字号放大后的布局。简历演示应突出“导入→定位→分析→验证变化”的完整任务，并同时说明静态推断、支持语言和问答验收边界；真实模型仍等待用户授权。

新增菜单、语言解析器或其他产品能力，仍须事先询问用户。本轮建议不等于擅自启动这些扩展。

## 6. 后续落实：同步闭环、覆盖可信度与窄屏布局

更新日期：2026-09-12。按用户确认继续优化已有功能，没有新增产品入口、语言解析器或数据表，也未执行真实远程同步、调用生成模型或推送 GitHub。

### 6.1 同步任务不再依赖当前菜单

`useProjectSynchronization` 挂载在 App 层，按项目分别跟踪用户提交的同步任务。“版本对比”只显示进度和结果，不再拥有任务轮询的生命周期。

- 同一项目重复点击只提交一次。离开菜单、切换项目后继续轮询；成功时先清除该项目的旧结构缓存，再刷新当前项目的数据。
- 当前项目同步成功后，结构明细、文件树、搜索、质量、图谱、源码查看及耦合对象失效。旧结构/报告响应即使晚到，也不能重新填回新界面。
- 项目 A 后台完成不会清空或覆盖正在查看的 B；再次进入 A 时读新结构和质量。无更新（`up_to_date`）只刷新元数据，保留索引阅读状态；同步失败不触发成功失效。
- 进度读取失败保留已知任务 ID，“重试读取进度”仍读取原任务，不再 POST。任务已完成但刷新失败时提示“重试刷新”，也不会再次下载或提交同步。
- 不自动重新生成分析报告，避免隐式调用用户配置的模型；旧报告失效后由用户使用现有入口重新生成。
- 应用关闭时回收轮询定时器并取消 GET，不取消已提交的后端任务。这不是跨浏览器关闭/重开后的任务恢复机制，也不是多客户端结果版本协议。

### 6.2 覆盖率以可用解析依据修正

之前支持扩展名就计入覆盖，可能把跳过或解析失败的文件算进去。现在基于已有数据库记录，区分语言支持文件数、可用解析文件数和解析问题文件数，排除有 `ParseIssue` 或超过 2 MiB 解析限制的文件，不重新读取用户源码。

合法空文件、常量文件即使没有符号或导入关系也不被判定失败；语法恢复产生的部分符号和风险仍保留供检查，但相应文件不算完整解析依据。

无可用结构解析依据的代码范围返回 `available=false`、`score/grade=null`，保留问题计数，实际权重为零。剩余可评分范围按原有 70/20/10 比例归一化。六类规则、规模归一化和基础风险惩罚没有修改，但评分输入改变可能导致综合分变化。

覆盖模型为 `recorded_parse_outcomes_v2`，综合评分输入版本为 `source_scope_weighted_size_normalized_v5`。API 增加兼容字段；前端显示、Markdown 报告与快照采用相同依据。快照历史/对比页遇到 `score_available=false` 显示 N/A，不展示内部数值占位；历史未知记录保留原值并通过提示标明覆盖口径未知。历史 JSON 不改写，新旧口径不被解释成修复或质量提升。

这里仍是**依据已保存结果与失败记录的保守估计**。历史索引没有独立的逐文件成功标志，因此不能把“没有失败记录”当作完整性的证明；未知文件类型也不能自动识别为源码。覆盖率不是测试覆盖率，静态结构分不代表业务正确、安全或缺陷概率。

### 6.3 质量页窄屏可读性

沿用绿色、直角、等宽字体及风险颜色。根据质量展示区的实际宽度重排筛选条和卡片：窄屏筛选每项独立一行，风险信息移至卡片顶部，长路径、标题、指标和不可用说明允许换行，不用隐藏溢出来掩盖缺失内容。

响应式回归覆盖 390/768/1440px × 应用现有 100%/120% 字号设置，以及 390px/120% 的四处 N/A 与长覆盖提示。验证控件边界、内容完整性、标题/指标不重叠和筛选仍可操作；没有宣称支持未提供的 125%/150% 应用设置。
