# 智能问答第一阶段：证据评测与检索修正

> 本文保留最初 36 道合成题的历史结果。2026-09-12 后续建立的 3 个真实仓库、60 道题及语义消融实验，见 [真实仓库评测](./QA_REAL_EVALUATION.md)。两套数据不可混算，真实生成回答仍待验收。

## 当前状态与边界

已完成离线评测基线、失败题分析、检索修正和回归门禁。尚未完成真实生成模型的回答质量验收：本次检查时没有已配置的生成模型，因此没有调用在线 API、没有运行本地生成模型，也没有产生模型费用。

评测集包含 **3 个自建合成源码样例、36 道带预期证据的题目**，不是 3 个真实开源项目。源码与标注由本阶段编写，可供维护者逐项复核；尚未经独立人工复核。该集合用于定位工程缺陷及防止回归，不是通用问答能力基准，也不能将通过率写成大模型回答准确率。

没有新增产品菜单或界面功能，没有推送 GitHub。现有问答仍然要求配置生成模型。

## 样例与题型

| 样例 | 源码形态 | 主要链路 |
| --- | --- | --- |
| accounts | Python API | 会话接口 → 登录函数 → accounts 查询 |
| orders | TypeScript API | 订单路由 → createOrder → orders 写入 |
| worker | Python 任务处理 | 导出入口 → 重试包装 → export_jobs 写入 |

这些是静态分析样例，不提供可部署服务或完整运行依赖；评测只解析文件，绝不执行仓库中的代码。

每个样例有 12 题：启动、实现定位、接口、数据库、修改影响、配置、测试、错误处理、连续追问、2 个不存在的目标，以及项目名称。共 27 道需要源码证据的题、6 道无证据题、3 道项目记录题。部分问题使用英文；同名生成代码和测试文件用于检验降权与排序。

- [cases.json](../benchmarks/repository_qa/cases.json)：问题、历史上下文、预期行为、文件路径/行号、关键原文和预期回答事实。
- [repos/](../benchmarks/repository_qa/repos/)：可直接检查的固定源码。
- [sources.json](../benchmarks/repository_qa/sources.json)：逐文件 SHA-256 锁；将换行统一为 LF 后计算，避免 Windows/Linux 换行造成误报。
- [phase1-comparison.json](../benchmarks/repository_qa/phase1-comparison.json)：修改前后摘要及逐题缺失证据记录。

源码哈希或证据标注不一致时，评测直接失败，不会自动改写预期答案。更新样例时必须同时复核标注与锁文件。

### 评分口径

- **必要证据 Recall@5**：前 5 条引用覆盖了该题多少条标注证据；文件相同、行号完整包含标注范围、摘录中包含标注的关键原文才算命中。只看文件名不计分。
- **MRR**：首条必要证据排名的倒数，按 27 道源码题平均；未命中为 0。不是所有必要证据都齐全的指标。
- **无证据拦截**：明确指定不存在的目标时，应返回证据不足，不得拿其他测试凑答案。这 6 题都使用了代码形态的明确名称，不代表所有无答案问题都能被识别。
- **引用合法性**：实际文件存在、范围有效、摘录匹配原文；不等于引用支持模型的全部事实结论。
- **检索通过**：预期路由正确、必要证据全部在前 5 位、全部返回引用合法；实现定位题还要求首条不是测试/生成代码。
- **连续追问**：使用固定的标注历史上下文，验证目标继承；尚未测试真实模型连续生成多轮历史后的偏移。

## 本次修正

1. 问答不再直接复用搜索列表的 5 行预览，而是从同一项目的真实索引分块补齐上下文。上限仍为每候选 24 行、1,600 字符，最终最多 8 条，避免无界扩张。
2. 函数符号引用保留紧邻的 Python 装饰器，避免只看到处理函数却丢失接口方法与路径。
3. 增强实际调用位置、测试函数体的排序；去掉已经包含在更完整引用中的重复短片段，减少 import 行占满结果。
4. 明确的代码名称优先于“接口、测试、配置”等扩展词。指定名称没有直接证据时，不再仅凭测试类别放行；保留受限的拼写容错。HTTP/JSON 等常见技术词不被误认为必须存在的函数名。
5. 中文新问题不再因为没有英文标识符就自动继承上一轮目标；英文追问词按词边界识别，避免把 with 中的 it 当成追问。
6. 引用校验新增源码内容哈希检查。源码在索引后改变或删除时，拒绝使用旧行号；同一文件在单次校验中只读取一次。修改源码后应先重新分析，再继续问答。

检索过程已抽为线上问答与评测共用的函数，离线评测不再需要伪造大模型回答来测试检索。

## 复现离线评测

从项目根目录执行（已有本地后端环境）：

```powershell
cd backend
.\.venv\Scripts\python.exe -m evaluations.repository_qa
```

已激活虚拟环境或 Linux CI 使用 `python -m evaluations.repository_qa`。

无需启动前后端。每次运行创建独立的内存 SQLite、源码副本和搜索索引，结果保存在项目目录下 `data/tmp/qa-eval/run-*/result.json` 与 `result.md`。不会读写日常项目数据库、已导入仓库或默认 API 配置。运行数据留在项目所在磁盘；当前项目在 D 盘，不使用 C 盘临时目录。

JSON 包含逐题证据、耗时、源文件哈希、问题集哈希及检索/生成适配相关代码哈希；Markdown 展示摘要和失败题。报告和测试索引属于已忽略的运行数据，不会随 Git 提交。每次结果保留用于排查，重复运行后可以按需清理对应的独立运行目录。

只执行指定题目：

```powershell
.\.venv\Scripts\python.exe -m evaluations.repository_qa --case accounts-05 --case orders-08
```

检索失败、模型错误或引用检查失败时命令返回非零退出码。离线题库已经接入 Pytest；CI 还会单独执行评测命令并输出摘要。

## 真实模型评测：待用户选择配置后执行

先在已有的“API 配置”中配置并测试生成模型。评测要求同时显式提供模型通道、配置文件路径及调用确认参数，不会默认使用用户的密钥或尝试收费接口。

例如选择已配置的 Ollama，先试运行单题：

```powershell
cd backend
.\.venv\Scripts\python.exe -m evaluations.repository_qa --provider ollama --provider-config ..\data\report-providers.json --allow-model-calls --case accounts-04
```

确认效果后去掉 `--case` 可运行全部题。在线通道使用相应 provider ID，例如 `openai-chat-compatible`；模型名称沿用配置，不会替用户选择付费模型。在线调用会发送该合成样例的相关代码和问题，并可能产生 API 费用。这里不会发送日常导入的私人仓库。

报告只记录 provider ID 与模型名称，不保存密钥、配置路径或服务地址。真实模型模式仍关闭语义检索，以先隔离生成阶段质量；混合语义检索的单独对照实验尚未完成。

模型返回后，维护者需结合 `expected_facts`、`citations` 和 `answer` 填写每题的 `manual_review`：

- 每个事实是否由所引用的原文支持，而不是仅出现一个合法的 `[1]`。
- 是否完整回答预期要点，有没有把测试代码/生成代码当作业务实现。
- 是否明确区分源码事实、静态推断和证据不足。
- 复核者及备注。

没有引用或模型超时会单独标注；有引用的回答仍标为“待人工复核”，工具不会自动宣称其事实正确。
