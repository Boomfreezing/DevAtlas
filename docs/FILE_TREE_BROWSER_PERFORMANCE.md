# 文件树长列表渲染与缓存回收

更新日期：2026-09-12。继[服务端分页阶段](./FILE_TREE_PERFORMANCE.md)之后，本轮仅优化已有文件树，不新增功能入口、数据库索引或模型调用，也未推送 GitHub。

本文保留单一宽目录阶段的实现与验收记录。后续已将窗口化预算扩展到多个展开目录，并加入目录读取并发控制，最新结果见[多目录文件树验收](./FILE_TREE_DENSE_PERFORMANCE.md)。

## 使用效果与实现

- 已读取文件超过 600 项时，按每组 200 行进行视口窗口化；远处文件页卸载实际文件行，保留高度占位，滚回时使用已读取数据恢复，不重新发起 API 请求。
- 目录节点本身不窗口化，继续保留真实组件和展开状态；追加文件页不会重新建立已展开的目录树。文件行使用 `memo` 减少无关重新渲染。
- 保留当前焦点页及相邻页，使 Tab 可以跨越第 199/200 等分页边界；文本选区涉及的页面暂不回收，避免滚动后无法复制已选中的文件名。焦点/选择退出后恢复正常回收。
- 高度来自 CSS 布局像素，不将包含 `body zoom` 的屏幕尺寸直接写回占位高度；未测页以现有 44px 文件行估算。90%/120% 显示比例及窄屏仍沿用原有样式。
- 缺少 IntersectionObserver 或 ResizeObserver 的浏览器回退完整渲染；小于等于 600 个已加载文件时也保持完整渲染。
- 折叠目录采用 LRU 缓存，非活跃缓存最多 4,000 条节点记录、64 个目录条目。正在展开的目录和未完成读取受保护，不会因为预算而消失。
- 单个折叠目录若超过 4,000 条记录，释放它自身，不清空其他小目录。之后重开会重新读取首批 200 项。菜单离开、项目/索引代际变更沿用原卸载行为，并清空整树缓存。
- 所有 observer、选择事件监听和读取作用域在退出时清理；缓存 pin 的释放句柄带身份校验，旧清理不会解除同一路径的新生命周期保护。

预算是**节点记录数，不是字节数或整个应用的内存硬上限**；活跃目录的数据量仍取决于用户已加载多少页。后端分页数量和文件总数没有减少，窗口化改变的是当前保留的 DOM。

## 测量口径

脚本：[file-tree-browser.spec.ts](../frontend/perf/file-tree-browser.spec.ts)。原始记录：[优化前](./performance/file-tree-browser-baseline.json)、[优化后](./performance/file-tree-browser-after.json)。

- 单一宽文件目录分别含 450、2,000、5,000 个文件，每档 3 个独立浏览器页面样本；页面先进入代码搜索，预热应用后再进入概览、展开并逐页追加。
- 所有业务 API 通过 Playwright 合成响应提供，不导入或执行源码，不调用模型，不接触用户数据库。前后两版保持同样分页数据与请求 offset 序列。
- 统计“已加载记录”依据真实请求 offset、返回数量及分页文字，不用较小的 DOM 数冒充未加载数据。
- 追加页耗时包括原生按钮 click 触发的真实 React 处理、等待分页更新和两帧绘制，以及自动化进程通信；其余交互使用 Playwright click。不是纯 React 渲染时间或生产后端端到端延迟。
- 使用本地 Vite 开发服务器（含 React StrictMode），固定 1440×1000 视口。没有执行生产构建浏览器性能对照。
- JS heap 在 Chrome CDP 强制 GC 后读取；这是诊断性 JS 堆，不是浏览器进程 RSS，也不是自然自动 GC 的观测结果。GC 不计入交互耗时。
- Long Task 记录覆盖整段样本，含初始化与诊断 GC，不能全部归因于某一次点击。
- 前后分开采样，未交替执行。优化前部分时段有其他单元测试进程，本机噪声未严格隔离；每档只有 3 个样本，因此不作统计显著性、P95 或固定提速比例承诺。
- JSON 保留浏览器、Node 版本、源码哈希与全部原始样本。baseline 是修改前现场记录；在当前代码上仅改 label 再执行，不能重建旧版本性能。

## 结果

下表均为 3 轮中位；Chrome 152.0.7977.83、Node 24.18.0、Windows。本阶段的浏览器数据不与上一阶段 service 查询耗时相加或替换比较。

| 累计读取文件数 | 首个 200 项 ms：前 → 后 | 最后追加页 ms：前 → 后 | 挂载文件行：前 → 后 | 强制 GC 后 JS 堆 MiB：前 → 后 |
|---:|---:|---:|---:|---:|
| 450 | 108.19 → 108.25 | 89.36 → 57.57 | 450 → 450 | 10.16 → 10.62 |
| 2,000 | 122.57 → 107.47 | 679.91 → 31.95 | 2,000 → 200 | 21.34 → 8.43 |
| 5,000 | 108.04 → 116.31 | 4,159.66 → 40.52 | 5,000 → 200 | 46.75 → 9.25 |

5,000 文件累计加载后的树内元素数为 40,008 → 1,635。行数 200 是本次固定视口的观测值，不是所有视口、焦点状态下的硬上限。

缓存重开：2,000 文件仍保留相同已读记录，1,042.72 → 72.90 ms，两版都没有额外目录请求。450 文件的重开为 109.17 → 143.71 ms，堆和少量包装元素也有增加；优化后重开计时增加了分页就绪检查，不对这些小差异作统计结论，更不能宣称所有规模均变快。

5,000 文件重开后读取量从全部 5,000 变为首批 200，优化后约 96.82 ms，本次开发环境有 2 次目录请求（StrictMode 首次挂载取消并重发）。该时间**不列为同比提速**。

折叠后的 JS 堆：2,000 文件约 6.19 → 6.20 MiB，5,000 文件约 6.55 → 6.05 MiB；离开菜单后两档均约 6 MiB。由此可见，本轮主要收益是减少展开状态的 DOM/组件，而非声称旧版折叠后保留了全部 DOM 或长期存在严重泄漏。

## 语义差异与限制

1. 2,000 文件在折叠缓存预算内，重新展开可对比同样的 2,000 条已读取数据。5,000 文件超过预算，优化后重新展开会读取首批 200 条并重新发起目录请求；**不能把这两次重开当作同数据量速度对比**。记录中单列重开后的已加载数与新增请求。
2. 菜单往返在两版都会卸载文件树，再返回根目录，不能宣称恢复了全部展开状态。离页后的堆观测也不能证明长时间运行绝无泄漏。
3. 这里只窗口化文件行；大量目录或多处同时展开、聚焦远处文件和跨页文字选择都可能增加 DOM。不保证整棵树始终只有 600 行。
4. 浏览器原生 Ctrl+F 不能完整检索未挂载的文件名，跨未挂载区域的全选/复制也不是完整仓库导出。已选中文件名的滚动保留经过测试；需要仓库内容检索时使用已有“代码搜索”，而非将浏览器查找视为全仓库搜索。
5. 文件页最多 200 行一组，组进入视口仍有一次渲染开销。未验证任意 CSS 自定义行高、屏幕阅读器的完整浏览流程或所有浏览器实现。
6. 尚未测量生产构建、并发用户、移动设备硬件、深层目录密集样本及长时间自然 GC。这些结果不能替代上述场景的验收。

## 复现优化后测量

从 `frontend` 目录运行：

```powershell
$env:DEVATLAS_TREE_BENCHMARK_LABEL = "after"
npx playwright test --config=playwright.performance.config.ts perf/file-tree-browser.spec.ts
```

工具使用工作区 D 盘独立临时数据和 8011/5175 测试端口；不要与其他浏览器测试并发运行。Windows 下测试环境须允许正常回收测试子进程。日常 8000/5173 服务不参与测量。

## 下一阶段建议

优先把已有长列表的验收补充到**目录密集、多目录同时展开、快速切换项目**场景，再评估依赖图谱的大图交互热点。先测量、再局部优化，不因单个宽目录数据变好就宣布所有大型仓库问题已解决。新菜单、持久化索引或新产品能力仍须先征求用户确认。
