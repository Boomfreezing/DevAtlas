# DevAtlas 项目评估与后续推进建议

评估日期：2026-09-12。检查基线：`915da89`，以及本次工作区优化。

本文件保留最初评估时点的发现与测试数字。后续已推进 [第一阶段问答检索评测](./QA_EVALUATION.md) 和 [第二阶段状态与版本对比可靠性](./STATE_CONSISTENCY.md)，最新测试基线以根目录 README 为准。

## 1. 整体判断

DevAtlas 已具备完整的本地仓库阅读与分析流程，适合演示和作为简历工程项目：导入仓库后可以查看结构、搜索源码、追踪依赖、查看质量风险、进行耦合分析、比较分析结果和导出报告。智能问答也已接入生成模型，并有检索和引用校验。

现阶段的主要差距是结果可信度、异常路径和可维护性。功能数量已足够；继续增加入口之前，应先证明现有分析在不同规模、不同语言、连续操作和失败重试时保持正确。没有统一的产品验收清单，不宜声称“完成度 95%”或“生产环境零缺陷”。

本次依据代码、回归测试和隔离端到端流程评估，没有调用用户的在线模型，也没有对用户已导入的远程仓库发起同步。测试覆盖率不能代替问答准确率或真实大仓库性能测量。

## 2. 现有功能的价值与边界

| 能力 | 当前价值 | 仍需完善的边界 |
| --- | --- | --- |
| 仓库导入、增量分析、远程同步 | 多来源输入、有界上传、后台进度、保留项目 ID 的同步 | 任务在本进程执行，重启后不能续跑；并发同步、重分析和删除的冲突需要进一步验证 |

| 依赖图谱与耦合分析 | 项目内导入、循环依赖和关联对象有可追溯来源 | 函数级关联属于有界静态推断，不是完整调用图；未发现测试不等于仓库没有测试 |

## 3. 本次已完成的优化

### 3.1 修复远端元数据与本地源码版本混淆

原问题可以稳定复现：本地源码仍在提交 A，先刷新 Git 元数据至提交 B，再同步仓库，旧逻辑会用已刷新的远端 HEAD 判断“无更新”，从而保留 A 却报告已是最新。

现在 `Project.source_commit` 单独记录成功导入或同步的源码版本。刷新提交记录只更新远端元数据；判断是否需要同步依据本地源码版本，且源码目录必须存在。

获得元数据后，导入和同步均按完整 Commit SHA 下载，避免检查远端与下载之间分支继续移动造成版本错配。只有新源码完整分析并成功替换后，才保存新的本地版本。失败测试验证原源码、项目 ID 和既有快照仍可用。

旧 SQLite 数据库自动补充可空字段，重复启动可安全执行。历史项目的本地版本保持未知，不从旧元数据推断；下一次用户主动同步时重新下载并建立绑定。增量分析检测到本地文件变更后清除原版本绑定。

### 3.2 修正报告来源与 Git 边界处理

报告将“源码 Commit”和“最近获取的远端 Commit”分别展示；只刷新提交记录不会改变分析基线。未绑定版本时明确说明。

另外修复默认分支名包含 `/` 时被错误拒绝，以及提交说明为空时访问不存在的首行导致异常的问题。

### 3.3 隔离端到端测试

Playwright 改为独立启动 `8011/5175` 服务，每次执行使用 `data/tmp/e2e/run-*` 下独立的数据库、仓库、临时目录、索引和模型配置。关闭已有服务复用，测试会校验初始项目列表为空。

这样测试结果不再取决于日常 `8000/5173` 服务是否启动、有哪些项目或是否已经配置生成模型。GitHub API 导入测试也改为完整模拟下载与元数据读取，不依赖真实 GitHub 网络。Pytest 的 API 测试同时隔离应用启动阶段的数据库迁移与临时目录，避免只覆盖路由依赖而遗漏启动逻辑。

## 5. 建议的推进顺序

以下验收标准是下一阶段目标，不是已取得的结果。

### 第一阶段：验证智能问答的实际效果

围绕现有问答准备至少 30 条人工标注问题，覆盖启动、功能定位、接口、数据库、修改影响、连续追问和仓库中无答案的情况，使用至少 3 个固定版本的样例仓库。

每题记录预期文件/行号、检索前 5 项是否包含必要证据、回答是否由证据支持、证据不足时是否拒答，以及总耗时。将“检索没有找到”和“模型读错证据”分开统计，然后针对低分题调整分块和重排。现有意图识别测试不能作为回答准确率证据。

验收：评测集、预期证据、模型与配置、实测结果可复现；单独列出未通过的问题。真实模型测试由用户选择已配置模型后运行，避免隐藏费用。

### 第二阶段：稳定跨项目操作与版本比较

重点测试快速切换项目、旧请求延迟返回、分析时删除项目、同步失败、分析缓存失效期间仍有旧计算在运行等场景。当前缓存构建在锁外执行，需验证旧计算不会在失效后重新填入过期结果。

快照应随数据保存评分模型版本和解析覆盖信息，并解释跨算法版本的差值，避免把算法变化算成“修复了问题”。这属于已有版本对比功能的可信度完善。

验收：延迟请求不会覆盖新项目；失败后原项目仍可阅读；跨版本比较具有明确口径。增加这些场景的独立 E2E，减少对单条综合流程的依赖。

### 第三阶段：性能与维护成本

对小、中、大三个固定仓库分别记录质量检测、搜索、切换项目的首次加载、缓存加载、P50/P95 耗时及内存峰值。此前质量计算的单次提速记录不能代表所有仓库和并发场景。

将集中了多个页面与状态的 `frontend/src/App.tsx` 按已有页面逐步拆分，统一请求取消和过期响应处理；整理两个样式文件中的重复覆盖。每次限定一个页面，通过行为回归后再继续。

验收：保留可复现的前后对比数据；可维护性改造不降低现有交互测试的通过率；优先补齐模型超时、认证失败、空响应等低覆盖路径，而非单纯追求总覆盖率数字。

### 第四阶段：交付展示

同步 README、使用报告、演示脚本和截图中的菜单名称与指标，使用干净环境验证启动流程，再录制 2～3 分钟演示。简历重点讲清“为什么这样设计、解决过什么问题、如何验证”，尤其是本次同步版本误判的复现和修复过程。

新增解析语言、全量函数调用图、用户体系、团队权限等属于功能扩展，按用户约定需要先确认范围。本次未新增产品菜单、未升级运行依赖、未推送 GitHub。
