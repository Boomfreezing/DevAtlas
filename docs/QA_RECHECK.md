# 离线检索复测与证据选择修复

日期：2026-09-12。本轮针对现有智能问答的检索环节，不新增产品菜单，不调用生成模型 API，不下载新的仓库或模型，不推送 GitHub。

## 评测范围

- 复用 [固定题库与仓库锁](../benchmarks/repository_qa_real/repositories.json)：Flask 开发集、Requests 验证集、Express 留出集，每组 20 题，共 60 题。
- 51 道源码证据题用于计算必要证据 Recall@5；6 道明确不存在标识符题测试拒答；3 道项目记录题测试路由。拒答结果不等于一般性幻觉率。
- 四组保持 `bm25`、`structured`、`hybrid`、`hybrid-rerank`，最后两组使用已经存在的本地 BGE 文件。默认离线模式不读取日常模型配置。
- 保留原题目、证据锚点、数据划分、最多 8 条引用、每条最多 1,600 字符等约束，不通过删除难题或放宽评分来提高数字。
- 修复只依据开发集与独立合成反例；验证集、留出集的逐题结果在实现冻结后用于最终记录，不据此继续调参。它们是同一公开固定题库，不是新采样的外部独立盲测。
- 所有运行使用内存 SQLite 与 D 盘独立源码副本、索引。不会执行被分析仓库代码，也不读写日常项目数据库。

## 指标解释

检索通过要求路由正确、全部必要证据进入前 5 条、引用合法；定位题还要求首条不是测试或生成代码。Recall@5 是每题必要证据召回比例的宏平均；MRR 使用最多 8 条返回证据中首个命中的排名，并非 MRR@5。

合法引用仅说明路径、行号和片段对应实际源码，不等于模型结论得到充分支持。没有生成调用，本轮 `answer_quality` 必须保持 `not_measured`。多轮题使用题库固定上下文，也不是实际模型连续对话验收。

每题耗时包含检索及当时的缓存状态，不含导入、模型加载和索引建立；各组顺序运行，存在系统缓存与本机负载差异。本轮不把单次 P50/P95 当成稳定性能结论。

## 本轮修复与约束

1. **先核验，再占引用名额。** 路径、行号和源码内容不合法的候选不再消耗最终引用名额；最多检查 64 个候选，每批 8 个，避免一次缓存大量完整源码。最终仍最多 8 条、每个文件最多 2 条。
2. **同文件的互补片段保留。** 不再仅凭代码文本相似度删除不同文件的实现。对同文件、同符号、源码版本一致且重叠的完整行窗口，尝试合并真实连续源码；合并不超过 48 行和 1,600 字符，不拼接缺失行或被截断的代码。
3. **保留定义与明确目标。** 函数体相似不应导致装饰器或定义头丢失；用户明确指定的目标优先于泛化别名，同时保留真实依赖关系指向的数据库/影响证据，避免只留下入口函数而丢掉下游语句。
4. **让评测失效可见。** 新版指纹覆盖应用/评测 Python 源码及两套评测的题库、源码锁与仓库清单 JSON，统一按 LF 文本计算。检测单组内及组间文件修改、新增、删除；一旦发现漂移，即使后续恢复文件，也保留失效标记，不把分数改成通过。评测输出 JSON 不属于输入，不纳入指纹，避免保存一份报告就使实现标识失效。

回归测试覆盖跨文件相似实现、失效候选补位、定义头与互补尾部、明确目标与扩展别名、真实依赖证据，以及候选/字符预算。它们使用独立合成反例，不通过新增真实评测标准答案实现修复。

指纹只约束观测时间点上的工作区源码，不是执行环境证明：不覆盖安装依赖、硬件或观测间被改动又恢复且未被捕获的文件。旧版报告的有限指纹与新版 `implementation_fingerprint_version=2` 范围不同，不能直接比较指纹数量或假装旧版已具有新版全部保护。

完整后端首次执行为 321 通过、1 失败：API 测试固定要求 `auth.py` 引用从函数定义第 3 行开始，而新整理结果合法合并了第 1–5 行连续上下文。已将该测试改为更直接的契约：完整定义必须位于片段对应的第 3 行偏移，整段正文严格等于真实源码切片，路径、符号、来源与引用预算均正确；不是仅放宽为包含函数名字。

最终后端 **322 项通过，覆盖率 86.29%**；Ruff 与 SQLite 资源警告严格检查通过。保留 1 条既有 Starlette/httpx 弃用警告，没有将其屏蔽。生产源码在最终四组对照开始后未再改动。

前端首次在嵌入计算和后端测试并行负载下为 334 通过、1 项文件树测试超过 5 秒；结束评测后按原命令、原超时门槛完整复跑，**335 项 / 25 个文件全部通过，TypeScript/Vite 构建通过**，未修改前端实现或提高超时限制。本轮没有重跑 Playwright；README 中既有 42 项浏览器结果属于上一轮验收。

## 后续推进建议

先验证既有**耦合分析**的关联正确性：用相同名称但不同模块、导入别名、重新导出、动态调用等反例检查误关联，将“没有找到”与“没有关系”严格区分。保留文件/行号证据及有界扫描，不重新引入已移除的全仓库函数调用图，不增加菜单。

本轮只读检查发现两个具体切入点（尚未在本轮修改）：

- `impact_analysis_service._symbol_references` 按短名字和单词边界匹配；`_called_symbol_candidates` 从函数文本提取标识符，再匹配项目内同名符号。应先补同名对象、`as` 别名、注释/字符串负例，验证接收者和导入绑定，避免把候选关系当成已证实调用。
- 风险计算中的 `test_coverage` 来自相关测试文件数与关联模块数的比值，不是真实运行得到的测试覆盖率。应补“测试文件只导入模块、实际测试另一个函数”的反例，再决定是否具有降低风险的证据。

随后基于已确认的关联修正风险评分与报告口径，避免误关联先放大影响范围、再抬高风险。检索侧剩余的跨文件多跳和有界证据组织问题应继续使用开发集回归；需要新的真实仓库、模型对照或端到端生成验收时，先确认范围与成本，不把本轮离线检索成绩当作生成效果。
