# 文件树服务端分页与性能验收

更新日期：2026-09-12。本轮只深化已有文件树与测试资源管理，没有新增菜单、数据库表、持久化目录索引、模型调用或 GitHub 推送。

## 改动与使用效果

旧实现虽然只展示当前目录的直接子项，但会先读取该目录下所有后代文件的完整 ORM 记录，在 Python 中聚合后一次返回。前一轮的 200 项限制只控制 DOM，不能减少网络传输和这部分 Python 分配。

本轮把目录计数交给 SQLite；直接文件不再参与不必要的分组聚合，与聚合后的子目录合并后统一排序和分页。每次只将当前页的行转换成 Python 响应对象。

- 根目录和子目录首批读取 200 个直接子项，点击“加载更多条目”才请求下一页。
- 目录在文件之前；保留 Unicode `str.lower()` 排序，原始名称及文件 ID 作为稳定的后续排序键。SQLite 连接内注册确定性小写函数，不改变数据库结构。
- `src`、`SRC` 分开处理，路径中的 `_`、`%` 是普通字符；文件数据不跨项目混入。
- 页请求失败不移除已加载内容，可重试原 offset。折叠、离页或项目变更取消等待并阻止旧响应写入缓存。
- 已成功的目录页可复用；分页统计、路径、偏移或条目异常时显示“重新读取”，重新读取该目录会清除对应后代缓存。
- 全量分析、有变化增量分析及同步成功沿用已有索引代际失效机制。界面保持绿色、直角、等宽 Terminal 风格。

### 接口约定

`GET /api/projects/{project_id}/files/tree?path=src&limit=200&offset=0`

| 字段 | 含义 |
|---|---|
| `path` | 当前读取的规范化相对目录 |
| `total_files` | 该目录下所有后代文件总数，不是当前页长度 |
| `total_items` | 当前目录的直接子目录数 + 直接文件数 |
| `items` | 本页直接子项；子目录的 `file_count` 仍是后代文件数 |
| `limit` / `offset` | 本次分页参数；默认 200 / 0，limit 范围 1–500 |
| `has_more` | 是否还有下一页；下次 offset = 本次 offset + 本次返回条目数 |

空仓库根目录返回 200 和零计数；不存在的项目/子目录返回 404；offset 超过最后一页返回 200、空 items 与真实总数。offset 范围为 0–2147483647，非法分页参数返回 422，非法目录路径返回 400。

新前端可兼容缺少分页字段的旧服务响应，并继续在本地分批展示。**上线应同时更新前后端并重启后端**：旧前端不识别新服务的分页总数，不能把新前端兼容旧服务误解成双向兼容。浏览器代码不执行被导入仓库中的源码。

## 可复现测量

脚本：[benchmark_file_tree.py](../backend/evaluations/benchmark_file_tree.py)。原始样本、实现哈希与环境：[file-tree-2026-09-12.json](./performance/file-tree-2026-09-12.json)。

- 500、5,000、20,000 文件的确定性 SQLite 元数据样本，不创建或执行仓库源码。
- 10% 为根目录直接文件，65% 位于宽目录，20% 位于八层深目录及其子目录，其余在其他目录；含大小写和 Unicode 名称。
- 每档测根目录、宽目录首屏、深目录首屏，共 9 个场景。测量前逐页拼接新结果，与冻结的旧算法校验全部节点、各字段、排序与计数，全部通过。
- 每个实现预热 2 次，11 轮交替运行新/旧实现；P50/P95 使用 nearest-rank，原始样本全部保留。
- 每次使用新 Session、复用连接，GC 在计时之外；SQLite 和操作系统缓存温热，未清理磁盘缓存。
- 计时仅包括 service 查询、行物化与响应数据整理，不包含 HTTP、JSON 编码、浏览器渲染和 Session 建立/关闭。
- 响应大小为紧凑 UTF-8 JSON 的未压缩字节数，旧实现是全部直接子项，新实现是默认首个 200 项。
- 内存另跑 3 轮 `tracemalloc`，不混入耗时计时。它是 **Python 分配峰值，不是进程 RSS，也不包含 SQLite 原生工作内存**。

环境：Windows 11、Python 3.13.5、SQLite 3.50.2、SQLAlchemy 2.0.52。不是生产环境或端到端性能承诺。

单位 ms；“深目录”不是只剩一个文件的目录，20,000 文件样本中它含 4,000 个后代文件、2,013 个直接子项。

| 500 | 根目录 | 3.345 | 2.048 | 3.971 | 2.469 |
| 500 | 宽目录 | 2.538 | 3.017 | 3.548 | 3.312 |
| 500 | 深目录 | 1.142 | 2.015 | 1.428 | 2.263 |

| 5,000 | 宽目录 | 39.776 | 17.725 | 45.518 | 19.529 |
| 5,000 | 深目录 | 12.832 | 10.211 | 13.868 | 16.206 |
| 20,000 | 根目录 | 271.506 | 42.407 | 315.144 | 44.543 |

| 根目录 | 2,003 → 200 | 326,020 → 32,600 | 36,158,886 → 286,642 |

### 复现

在项目的 `backend` 目录运行，所有运行数据写在工作区 `data/tmp` 下：

```powershell
.venv/Scripts/python.exe -m evaluations.benchmark_file_tree --output ../docs/performance/file-tree-2026-09-12.json --work-dir ../data/tmp/file-tree-benchmark --samples 11 --warmups 2 --memory-samples 3
```

脚本禁用模型及网络连接，不读取用户数据库或 provider 配置。不要在并行跑重负载测试时用所得数字与本报告直接比较。9 项轻量测试验证样本可重复性、分页等价检测、统计与边界，不把大样本计时作为 CI 耗时断言。

## 已知边界与下一步

1. 这是减少 Python 物化和首屏传输，不是让数据库查询与目录大小完全无关。SQLite 仍需扫描、聚合和排序；没有新建目录索引，每一页也会重新执行查询。全量翻完的耗时尚未作为性能指标测量。
2. 不限制用户逐页展开后累积的 DOM 数；加载很多页后仍可能卡顿。下一阶段优先测量并优化现有文件树长列表的渲染、折叠释放和菜单往返内存，再决定是否在同一组件采用虚拟渲染。
3. 请求取消不代表已经开始的后端 SQL 立即停止。尚未测量服务进程 RSS、并发大目录请求或冷启动磁盘延迟。
4. 当前窗口重分析会使缓存失效，跨页总数变化也可检测；其他客户端造成等计数内容替换仍可能漏检，因为没有跨页索引版本游标。
5. 若后续需要持久化目录索引、新的游标协议或新产品能力，先说明代价并征求用户确认；本轮不增加这些范围。
